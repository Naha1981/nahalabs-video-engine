# NahaLabs Messaging Platform (WhatsApp) Skill — ADR-014

Self-owned, multi-tenant, direct WhatsApp Web infrastructure. **No Twilio, no Evolution API,
no 360dialog, no paid WhatsApp Cloud API, no NoClick.** One shared Operator serves **all** NahaLabs apps.

Full contract + reference code: [`references/whatsapp-operator-contract.md`](references/whatsapp-operator-contract.md).

---

## 1. Two-component split (crucial rule)

Never put the WhatsApp socket in the same codebase/host as the serverless frontend.

| Component | Where | Owns |
| :--- | :--- | :--- |
| **Core (Brain)** | Next.js on Vercel | UI, Clerk auth, Neon/Postgres business data, tenant isolation, AI, outbox, durable jobs, webhook receivers |
| **Operator (Engine)** | Node.js + `@whiskeysockets/baileys` on Render/Docker/Fly.io | Persistent 24/7 sockets, QR pairing, send/receive, delivery state, `/health`, signed HTTP |

Core and Operator communicate **exclusively via HMAC-SHA256-signed HTTP** (constant-time compare).

---

## 2. Handshake & security

- **Operator → Core (inbound):** `POST` to `/api/webhooks/whatsapp` with a signature over
  `timestamp + nonce + raw body` (HMAC-SHA256, `crypto.timingSafeEqual`). Core verifies, persists,
  enqueues a durable job, returns **200 fast**.
- **Core → Operator (outbound):** call `POST /send` with `Authorization: Bearer $OPERATOR_API_KEY`.
- Business code calls `sendMessage(...)` via a **typed platform client**
  (`src/lib/integrations/messaging-platform/platform-client.ts`). It **never** imports Baileys.

---

## 3. Identity & multi-tenancy

- Fundamental identity = **`wa_account_id`** (one connected WhatsApp number).
- `wa_sessions` (PK `wa_account_id, key`) holds Baileys `BufferJSON` creds — **raw `pg`**, auto-created on boot.
- **INV-1:** ONE live socket per `wa_account_id`, no matter how many apps/tenants bind to it.
- `wa_account_bindings` maps `(app_id, tenant_id) → wa_account_id → webhook_url`.
- One Operator, many apps: each app has its own `/api/webhooks/whatsapp` route; the Operator fans out
  one idempotent `inbound_delivery` **per active binding**.

---

## 4. The two QRs (critical — do not confuse them)

1. **Pairing QR (link-a-device)** — generated by the Operator when the owner clicks "Connect WhatsApp".
   Ephemeral, TTL-bounded, **never stored in Postgres** (memory/Redis only). The **business owner**
   scans it once with their phone to link their number.
2. **Customer chat QR / `wa.me` link** — a **stable** QR (`https://wa.me/<number>?text=…`) shown in the
   owner's dashboard for **customers** to scan and start a conversation.

They are different artifacts with different audiences. Never reuse the pairing QR as the customer QR.

**Owner activation flow (the "Thandi" experience):**
```text
Tenant signs up → clicks "Connect WhatsApp" → Core asks Operator to create a socket for a new
wa_account_id → Operator returns an ephemeral PAIRING QR → owner scans with phone (once) →
Operator saves encrypted creds → owner's dashboard shows the stable CUSTOMER chat QR / wa.me link →
customers scan that → Operator receives, signs, POSTs to Core → Core AI replies via Operator →
owner's phone can be switched off; the session lives on the Operator 24/7.
```

---

## 5. Message flows

**Inbound (customer → AI):**
`Operator receives → persists platform_event → resolves bindings → idempotent inbound_delivery per
binding → signed webhook → Core verifies HMAC → persists inbound message → enqueues PlatformJob →
200 fast → worker (SELECT … FOR UPDATE SKIP LOCKED) → AI (Vercel AI SDK) → reply → OutboxMessage`.

**Outbound (AI → customer):**
`Dispatcher polls OutboxMessage (SKIP LOCKED) → Operator /send (signed) → Baileys send →
delivery status update → retry with backoff → dead-letter after 5 attempts`.

---

## 6. Safety, control & compliance

- **Master switch:** a **database-backed** toggle (not an env var) that instantly kills AI processing
  globally without redeploy.
- **Manual mode:** per-tenant toggle — log messages but forbid the AI from replying.
- **POPIA/GDPR:** natively detect `STOP / UNSUBSCRIBE / OPT-OUT` and add the sender to that tenant's
  blocklist immediately; never message a blocklisted number.
- **Keep-alive:** Render free instances sleep; keep the Operator alive with an **external scheduler**
  (cron-job.org) hitting `GET /health` every ≤10 min — never a browser timer. Handle `SIGTERM`
  gracefully (close sockets, release locks).

---

## 7. Observability & invariants

- Trace envelope on all logs: `traceId → appId → tenantId → waAccountId → messageId → jobId → deliveryId`.
- Never display "Delivered" unless delivery state is actually reconciled.
- Guarantee exactly the states: `pending → queued → processing → sent → delivered → failed / unknown`.
- The Operator auto-creates its own tables on boot; Core migrations are managed by Drizzle.
- A cross-account message leak is **Sev-1**.

## Guardrails for the coding agent

- Do **not** import Baileys into Core code. Do **not** store pairing QRs in Postgres.
- Do **not** run the socket inside a serverless function. Do **not** introduce Twilio/Evolution API.
- Wrap every `sendMessage` side effect in the outbox; every `/send` call is idempotent.
